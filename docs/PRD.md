# Headly — 疼痛管理 App 产品需求文档（PRD · 头痛阶段）

- **版本**：v0.3（草案）
- **日期**：2026-07-03
- **平台**：iOS（SwiftUI，iPhone 优先）
- **愿景**：更好地管理疼痛，并最终消灭疼痛；本阶段以头痛为切入点。
- **文档目的**：明确 Headly 的愿景与切入策略、产品定位、竞品差异、功能范围与 MVP 边界，作为设计与开发的依据。

---

## 1. 愿景与使命

> **Headly 的长期愿景：更好地管理疼痛，并最终消灭疼痛。**

疼痛是人类最普遍、也最被低估的健康负担——从头痛、颈肩腰背痛到痛经、慢性神经痛，全球有超过 20% 的人长期与某种疼痛共处。疼痛管理的第一步是让疼痛被看见：被规律地记录、被科学地归因、被医生准确地理解。

我们选择**从头痛切入**，原因是：

- 头痛是患病率最高、就诊需求最明确的疼痛类型，"头痛日记"有明确的临床共识做支撑；
- 头痛的"发作—诱因—用药—疗效"闭环最完整，最适合验证记录与洞察的产品模型；
- 头痛人群的痛点（发作时难以操作、找不到诱因、复诊说不清）在现有产品中远未被解决好。

头痛只是起点。在头痛场景验证"低成本记录 → 诱因洞察 → 医生报告"这条价值链之后，Headly 将逐步把同一套能力扩展到痛经、颈肩腰背痛等更多疼痛类型，成为一个**通用的疼痛管理平台**。本文档聚焦第一阶段：头痛记录。

## 2. 背景与机会

头痛（尤其是偏头痛）是全球致残率最高的疾病之一，患病率约 15%，且以 20–50 岁人群为主。头痛管理的临床共识是：**长期、规律的头痛日记是识别诱因、评估药物疗效、辅助医生诊断的核心工具**。纸质日记依从性差，App 是天然载体。

海外市场已有成熟产品（Migraine Buddy 装机量 400 万+），但普遍存在三个问题：

1. **记录成本高**——发作时用户畏光、恶心，却要在多个表单页之间点选；
2. **隐私顾虑**——主流产品云端存储、部分与药企关联；
3. **中文市场空缺**——国内几乎没有体验良好的头痛记录 App，多为小程序或通用健康记录工具，缺少针对头痛的诱因分析与医生报告。

Headly 的机会：做一款**记录极快、数据本地优先、面向中文用户、能产出医生可用报告**的头痛记录 App。

### 3.2 核心结论

1. **"发作中可用"是最大的体验分水岭**。老牌产品（Migraine Buddy）功能全但记录链路长；新产品（Migraine Trail、Migra）都在拼"10 秒内完成记录"，用语音、一键快捷方式降低发作时的操作成本。
2. **诱因分析是留存的核心价值**。用户坚持记录的动力来自"发现了自己的诱因"。N1-Headache 的做法最科学：区分"诱因 / 保护因子 / 无关联因子"，避免用户误信错误归因。
3. **医生报告是刚需且是就诊场景的信任来源**。所有头部产品都提供 PDF 报告；MIDAS、HIT-6 等标准化量表是神经科门诊的通用语言。
4. **天气（尤其气压变化）是被验证的高频诱因**，从"回顾记录"走向"提前预警"是行业趋势。
5. **隐私本地化成为新卖点**。Migra、Migraine Trail 均以"数据不出设备、不卖数据"为核心宣传点，反衬了 Migraine Buddy 的云端 + 药企背景争议。
6. **社区不是必选项**。只有 Migraine Buddy 的社区形成规模，后来者均放弃社区，聚焦工具价值。

### 3.3 Headly 差异化定位

> **给中文头痛患者的、发作时 10 秒可完成记录的本地优先头痛日记，帮你找到诱因，并生成医生看得懂的报告。**

- 对标 Migraine Buddy 的记录完整度，但把默认记录流程压缩到 3 步以内；
- 借鉴 N1-Headache 的诱因/保护因子分析框架；
- 本地优先（SwiftData + 可选 iCloud 私有同步），不做账号强制注册；
- 深度接入 Apple 生态：HealthKit（睡眠/经期/心率）、WeatherKit（气压）、Widget/快捷指令/Apple Watch 一键记录。

与竞品最本质的差异在于愿景：竞品都把自己定义为"偏头痛工具"，而 Headly 把头痛视为疼痛管理平台的第一站——"记录 → 归因 → 报告"这套核心能力从设计之初就按可复用到其他疼痛类型来构建（见第 1 节愿景与 7.5 节远期路线）。

## 4. 目标用户与场景

### 4.1 目标用户

| 用户群 | 特征 | 核心诉求 |
| --- | --- | --- |
| 偏头痛患者（核心） | 每月发作 1–10 次，多为 20–45 岁女性 | 找诱因、评估药效、复诊时说清楚病情 |
| 慢性/紧张性头痛人群 | 发作频繁但强度较低 | 低成本记录频率与用药，防止药物过量性头痛 |
| 就诊准备者 | 医生要求记头痛日记 | 快速产出规范的头痛日记报告 |

### 4.2 关键场景

1. **发作中**：畏光、恶心、只想闭眼。要求：暗色界面、大按钮、一步记下"开始了"，其余细节稍后补。
2. **发作后补记**：疼痛缓解后补全疼痛位置、强度峰值、症状、用药与疗效。
3. **每日打卡（可选）**：无发作日快速记录睡眠、压力、饮食等因子，为诱因分析积累对照数据。
4. **复诊前**：一键生成近 1/3 个月报告 PDF，包含发作频率、用药情况、MIDAS 评分。
5. **日常预防**：收到"未来 48 小时气压骤降"预警，提前规避其他诱因。

## 5. 功能需求

优先级：P0 = MVP 必须，P1 = 第二版本，P2 = 远期。

### 5.1 头痛记录（P0）

- **快速开始**：首页超大"记录头痛"按钮，一次点击记录发作开始时间；支持锁屏 Widget、快捷指令、Apple Watch（P1）触发。
- **发作详情**（可发作中填，也可事后补全）：
  - 疼痛强度：0–10 滑杆，支持记录发作过程中的强度变化；
  - 疼痛位置：头部图谱点选（左/右/双侧、前额/太阳穴/后枕/眼周）；
  - 疼痛性质：搏动、压迫、刺痛、胀痛等；
  - 伴随症状：恶心、呕吐、畏光、畏声、先兆（视觉闪光等）多选；
  - 结束时间 / 一键"仍在发作"。
- **发作中模式**：进入记录即切换纯暗色、低亮度、大字号界面。
- 编辑、补录、删除历史记录。

### 5.2 诱因与因子记录（P0 基础 / P1 分析）

- P0：发作时勾选可疑诱因（预置中文语境诱因库：睡眠不足、压力、月经、饮酒、咖啡因、漏餐、屏幕时间、颈肩劳损、天气变化……），支持自定义。
- P0：自动附加环境数据——记录发作时的天气、温度、气压及 24h 气压变化（WeatherKit）。
- P1：每日因子打卡（睡眠、压力、心情、饮水、运动），30 秒内可完成；HealthKit 自动导入睡眠、经期、运动数据减少手动输入。
- P1：**诱因分析报告**——基于至少 6–8 周数据做统计关联，输出"疑似诱因 / 疑似保护因子 / 无明显关联"三类结论，明确标注置信度，避免误导。

### 5.3 用药管理（P0）

- 个人药箱：常用药列表（预置国内常见药名：布洛芬、对乙酰氨基酚、佐米曲普坦、利扎曲普坦等），记录剂量。
- 发作记录中关联用药：服药时间、剂量、2 小时后疗效（无效/缓解/完全缓解）。
- 用药统计与**药物过量性头痛（MOH）预警**：急性期用药 ≥10 天/月时提醒（P1）。

### 5.4 统计与洞察（P0 基础 / P1 增强）

- P0：日历视图（头痛日一目了然）、月度统计（发作次数、头痛天数、平均强度、平均时长、用药天数）。
- P1：趋势图（频率/强度随时间变化）、诱因排行、时段分布、天气关联图。
- P2：发作风险预测（结合气压预报 + 个人历史模式）。
- P2：**端上 AI 洞察**——基于系统端侧大模型的自然语言总结（"近三个月你的头痛模式"），全程在设备上运行，详见 7.6 节 AI 演进路径。

### 5.5 医生报告（P0）

- 一键生成 PDF：选定时间范围内的发作列表、频率统计、用药记录、诱因摘要。
- 内置 **MIDAS**（每 3 个月）与 **HIT-6** 量表自评，评分写入报告（P1）。
- 系统分享面板导出（微信/邮件/打印）。

### 5.6 提醒与预警（P1）

- 记录提醒（每日固定时间温和提醒补记）。
- 气压骤变预警（未来 48h）。
- 服药提醒（预防性用药人群）。

### 5.7 数据与账户（P0）

**产品原则：无登录。** Headly 不引入任何形式的账号注册与登录，全部能力基于 Apple 生态实现：

- 本地优先：SwiftData 本地存储，下载即用，无需注册即可使用全部核心功能；
- 同步：iCloud 私有数据库（CloudKit），换机、多设备不丢数据，开发者服务器不存储任何健康数据；
- 订阅：StoreKit 绑定 Apple ID，"恢复购买"找回权益，无需自建账号体系；
- 数据导出（CSV/JSON）与完全删除。

该原则带来的取舍已确认接受：数据同步锁定 Apple 生态（Android/Web 版届时另行方案）；不做任何服务端用户功能；用户数据丢失只能依赖 iCloud 与手动备份，因此设置页需明示 iCloud 同步状态并提供导出备份。若远期确需跨平台或医生协作，再以 Sign in with Apple 引入**可选**登录，存量数据平滑迁移。

### 5.8 明确不做（现阶段）

- 社区/社交功能；
- 在线问诊、电商卖药；
- Android 版本（验证后再评估）；
- 任何形式的用户数据售卖或广告。

### 7.5 远期路线：从头痛到疼痛管理平台

在头痛阶段验证核心价值链后（判断标准：留存与医生报告使用率达到第 9 节指标），按疼痛类型逐步扩展：

1. **痛经**：人群与偏头痛高度重叠（20–45 岁女性），周期性强、与经期数据天然打通，是复用"记录 → 归因 → 报告"能力成本最低的第二站；
2. **颈肩腰背痛**：久坐人群基数大，与姿势、运动、工作习惯等因子关联，可复用因子打卡与洞察框架；
3. **慢性疼痛通用化**：开放自定义疼痛类型与身体图谱，配合标准化疼痛量表（如 BPI），面向慢性疼痛患者与疼痛科门诊。

为此在架构上的要求：数据模型、诱因库、报告模板均按"疼痛类型可插拔"设计（见附录 B），避免头痛逻辑硬编码。

### 7.6 AI 演进路径：端上优先

**技术原则：AI 分析优先在设备端完成**，与"无登录 + 数据不出设备"的产品定位保持一致。分三层演进：

1. **统计分析（v1.2，非 LLM）**：诱因分析报告基于单用户数据的统计关联，纯端上计算，是洞察价值的基本盘，不依赖大模型；
2. **端上 LLM 洞察（远期主路线）**：基于 Apple Foundation Models 框架调用系统端侧大模型，做自然语言洞察——如"用一段话总结你近三个月的头痛模式"、报告摘要生成、记录时的自然语言输入解析。零 API 成本、离线可用、隐私承诺不打折，"AI 分析也在你设备上完成"本身即是卖点。接受其能力边界：不做超长报告与深度多轮推理；
3. **云端 LLM（备选，仅在端上能力确实不满足时评估）**：若引入，必须满足四个前置条件——功能明确 opt-in 且单独同意；端上先聚合脱敏，只上传统计摘要而非原始日记；经无状态代理调用国内已备案模型（不自存数据、API Key 不进客户端）；以 App Attest + StoreKit 订阅凭证做防滥用与配额控制，仍不引入登录。

对架构的当前要求：诱因分析与洞察模块的输入统一定义为"聚合后的特征摘要"而非原始记录，使统计分析、端上 LLM、（假如未来需要的）云端 LLM 共用同一数据接口，且天然满足数据最小化。

## 8. 商业模式（初步）

免费 + 订阅（参考竞品定价 ¥12–18/月 或 ¥68–98/年）：

- **免费**：无限记录、日历统计、基础 PDF 报告——记录本身永远免费（信任基础）。
- **订阅**：诱因分析报告、气压预警、高级图表、报告自定义、端上 AI 洞察（远期）。

得益于端上 AI 路线（7.6 节），AI 功能没有按次的 API 成本，订阅定价无需为推理成本留出空间，毛利结构比云端 AI 竞品更健康。

## 9. 成功指标

- 激活：新用户 24h 内完成首条头痛记录比例 ≥60%；
- 记录成本：快速记录中位耗时 ≤10s；
- 留存：次月留存 ≥35%（健康记录类基准约 25%）；
- 价值验证：使用 ≥8 周用户中生成过医生报告的比例 ≥30%；
- 商业：v1.2 后订阅转化率 ≥3%。

## 10. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 记录疲劳导致流失 | 默认最简记录；每日打卡设为可选；Widget/Watch 降低成本 |
| 数据量不足导致诱因分析不可信 | 分析报告设最低数据门槛并展示置信度，宁缺毋滥 |
| App Store 健康类审核 | 全程免责声明；不做诊断表述；隐私营养标签如实填写 |
| 竞品中文化 | 靠本地诱因库、中文药品库、微信分享报告等本土体验建立壁垒 |
| 端上模型能力不足以支撑洞察体验 | 洞察模块输入统一为特征摘要（7.6 节），必要时可切换云端方案而不重构；同时统计分析保证基础价值不依赖 LLM |
| 端侧大模型依赖较新机型/系统 | AI 洞察作为订阅增值项而非核心功能；老机型降级为纯统计分析 |

## 附录 B：核心数据模型（草案）

为支撑远期"多疼痛类型"扩展（7.5 节），核心实体以"疼痛发作"抽象命名，头痛作为第一个疼痛类型实现：

- `PainEpisode`：疼痛类型（v1.0 仅 headache）、开始/结束时间、强度（含变化序列）、位置（按疼痛类型使用对应身体图谱）、性质、症状[]、诱因[]、天气快照、备注
- `MedicationIntake`：药品、剂量、服用时间、疗效评价、所属 Episode
- `Medication`：名称、类型（急性/预防）、默认剂量
- `DailyFactorLog`（v1.1）：日期、睡眠、压力、心情、自定义因子
- 诱因库、症状库、报告模板均与疼痛类型关联，按类型可插拔
